## What does not work / pitfalls

| Symptom | Conclusion |
|---|---|
| COM reopen after DONE (CreateFile hang ~8–9 s) | Zombie COM; the short-open race earlier also missed |
| Same-handle FH after DONE (WinUSB) | empty nop ~3 s × 6; **holds the handle and eats the window** |
| `r.connect()` in the parent after DONE | hangs ~7 s → errno 19; kills the FH window |
| Probe child stdout | importing edl prints `Capstone library is missing` → the parser took the token **Capstone** instead of ACK/MISS |
| Waiting only for post-logo | After the logo it is always **SAHARA** → FH **never** stayed on USB |
| Spam open every 0.3 s on rising edge | can kill a slow first open; after a settle of 0.8–1 s the open is sometimes OK (we get SAHARA) |
| `pnputil /update-driver` | this Windows build does **not** have that command → the old elevated script dumped `/?` |
| Zadig / SAFE_BUMP / parallel agents | still NO |

## Working hypothesis (state at 18:48)

Sahara accepts the melf (END/DONE OK), then the tablet goes into the **logo / reboot
path** and returns to EDL Sahara.
Firehose **does not stay** on the bus (or never starts at all).
The "zombie before drop" window (~8 s while 9008 is still PnP-present) is the better
candidate for FH than post-logo; post-logo = too late (EDL fallback).

## Discovery 18:49 — pre-DONE nop = hang

After `END 0x0`, attempting a same-handle `fh_xml(nop)` **before** `cmd_done()` hangs
the WinUSB pipe:

- the log stops at `END 0x0` (no DONE line),
- the process hangs, 9008 PnP still OK,
- DONE never comes out → ruins the whole logo/FH cycle.

**Fix:** after END go straight to `DONE`, no pre-DONE peek. Zombie/logo race only
after RELEASE.

## Run 18:54 (no pre-DONE)

- DONE True OK (pre-DONE hang fixed).
- Zombie 8 s: all **hang-kill** on 9008 (a WinUSB zombie cannot be opened).
- USB absent OK ~8 s after DONE (logo).
- Reconnect 900E → **SAHARA** (FH did not stay).
- Retry `prog_firehose_ddr_lenovo.elf`: `conn {'mode': 'error'}` — HELLO already
  consumed/ruined by the probe child; upload failed.
- FAIL on the melf path.

### Conclusions

1. A zombie WinUSB is always a hang (like COM) until the drop.
2. Post-logo is only EDL Sahara.
3. The alt-loader retry must: after SAHARA from the probe → `RESET_STATE` / a fresh
   HELLO, or upload in the same open as the detection (not a blind second connect).

## Run 18:57 — RESET_STATE OK, alt elf empty END

- DONE + zombie hang-kill + logo absent — as before.
- Reconnect SAHARA → `RESET_STATE` → fresh HELLO **ver=2 mode=2** OK.
- Upload `prog_firehose_ddr_lenovo.elf` on **900E**: COMMAND→ITX→**empty END loops=0
  sent=0** → fail.
- Conclusion: after the logo we are on 900E in COMMAND mode; the small elf never gets
  a READ (same as the bump empty END). You must **bump 900E→9008**, then full melf
  (or elf) on 9008 — not ITX on 900E.

## Run 18:59 — second-shot bump fail

- First cycle: DONE/zombie hang/logo/SAHARA — unchanged.
- `bump + reupload`: **`900E conn mode=error`** — the SAHARA probe ate the HELLO
  before the bump opened the port.
- Fix: before the bump in a retry → **RESET_STATE on 900E**, only then
  `bump_900e_to_9008` + melf.

## Run 19:01 — second shot Sahara OK, FH still zero

- RESET_STATE → bump → 9008 → **second full melf END/DONE OK** (1 554 996 B).
- Zombie again hang-kill → logo absent → reconnect **SAHARA**.
- Hard conclusion: **repeatable Sahara success ≠ firehose on USB**. Neither the first
  nor the second shot leaves FH on the bus (WinUSB). After DONE the programmer goes
  into the logo/reboot → EDL.

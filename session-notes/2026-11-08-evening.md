## 3. The FULL VIP sequence (from bkerler/edl PR #829)

```
1. digest table                      -> raw packet, no XML
2. <verify value="ping" EnableVip="1"/>   <- THE EXACT COMMAND
3. Sign.bin (256 B padded to 4096)    -> raw packet
   expected response: "verify passed."
```

After the handshake, every read/write must carry `label="partition_name"`;
for GPT one uses `label="PrimaryGPT"`.

### The VIP code IS in our programmer

Strings from the image @`0x110B50` of the melf (the same code as in
`prog_firehose_ddr.elf`):

```
Requesting VIP img authentication elf_buf = 0x%x, elf_buf_len = %d
VIP img authentication failed with smc_status = 0x%x, rsp_0 = 0x%x
VIP is enabled, receiving the signed table of size %d
Number of VIP hashes %d on initial table
VIP hash table accepted %d packet %d
VIP data verified table %d packet %d
Last packet received, re-initializing VIP %d %d
```

### What we do NOT have

There is no digest table in the ROM package (checked: no `Digest.elf`/`Sign.bin`, no
magic `0x7CEF0312`). It is not in the database of 2 745 loaders either.
For SM8650 only these exist: Xiaomi `SNAPDRAGON 8 GEN 3.melf` and OPPO
`SM8650_New_Chimera_V1.0.21.melf` + `Digest.elf` — no Lenovo.

**But that does not block the test:** if the programmer is in VIP mode, it will print
`VIP is enabled, receiving the signed table of size N` itself — and we will see it.

## 4. Offline melf analysis — the hash segment IS read

PBL asks for `image_id=0xd` (13), then for specific ranges. The sum of the first
12 requests = 202 172 B, target 1 554 996 B.

Key: among the requests there is `off=197376 len=11376`. That is the **hash segment of
image [1]**:

```
image [1] @0x1300, ELF32, type=EXEC, machine=0xf3, entry=0x20412d00
ph[11] type=0x02000000 (Qualcomm hash) off=0x2f000 filesz=0x2c70 (11376)
0x1300 + 0x2f000 = 197376   <- exactly the requested offset
```

**Conclusion:** PBL reads the hash table and verifies it. `END status=0x0` is a genuine
authorisation success, not an artefact. The programmer is accepted and authenticated —
the problem lies entirely in what happens **after `DONE`**.

## 5. What we never did

All ~40 sessions sent `<configure/>` ~1 ms after `DONE` and read the response.
**Not one of them read what the programmer prints on its own.**

The script `banner_capture_2026-11-08.py`:

```
1. listen for 05C6 every 50 ms
2. bump 900E -> 9008 (proven mode-switch sequence)
3. Sahara upload of the melf, strict framing
   REJECTS a false END 0x0 at bytes=0 (requires >= 1 554 996)
4. DONE
5. PASSIVE: send nothing, just read for 6 s   <- NEW
6. if silent: nop / getstorageinfo / configure+label / configure bare
```

Flags: `--budget`, `--attempts`, `--short-melf` (uses `xbl_s.melf`, which is exactly the
1 117 008 B prefix of the devprg), `--no-probe`.

## 6. Battery

The tablet drains quickly because it **does not sleep** — the loop
logo → crashdump → reset is continuous CPU/DDR/UFS work. Add to that the DBC in the
programmer:

```
charger is not charging and device will shut down
No battery, Shutdown!
battery recover failed
Loader dbc skipped. VBAT: %dmV
```

At low VBAT the programmer shuts the device down instead of starting.
That explains the night's degradation (1 554 996 B → 16 700 B) and the clean cycle
after 9 h of charging.

**Rule:** test only on a charged tablet, preferably with the charger connected.

## DISCOVERY 1 — `0x29` is an ELF64 format rejection, not a signature rejection

Sizes and headers:

```
xbl_s_devprg_ns.melf      1 569 028 B   ELF32  machine=0x01 (EM_ARM)   entry=0x22126000
prog_firehose_ddr.elf       303 096 B   ELF64  machine=0xB7 (AArch64)  entry=0x149997A8
```

Sahara reads the 64-byte header and **after that** returns `0x29`.
`0x29` **does not exist** in the protocol table (which ends at `0x28`) — it is a
vendor NAK.

Conclusion: this PBL accepts **only a melf** (ELF32 with a hash table) and rejects a
plain ELF64 — regardless of which package it came from. That is why "Method A/B" with
`prog_firehose_ddr.elf` had no chance of working, and no package version would have
changed it.

## DISCOVERY 2 — the correct reset is `SAHARA_RESET` (0x07), not `RESET_STATE_MACHINE` (0x13)

```
SAHARA_RESET (0x07)            -> RESET_RSP (0x08)   WORKS
RESET_STATE_MACHINE (0x13)     -> Pipe error          KILLS THE CONNECTION
```

All the earlier scripts in the kit used `0x13` as a "safe reset". That was the bug —
it was exactly what left subsequent attempts with nothing to talk to.

## DISCOVERY 3 — Sahara packet framing (a bug in our scripts)

`read()` on bulk IN returns **as many bytes as are available** — it can contain
**several Sahara packets at once**. The earlier scripts read 65 536 B and parsed only
the first header, losing the rest.

Effect: desynchronisation → responses to the wrong offsets → `0xD`.
(`0xD` = `SAHARA_NAK_READ_DATA_ERROR`.)

Fix: a byte buffer, always consuming **exactly `length`** from the header.

## DISCOVERY 4 — edlclient `usb_class` does not work on this host, raw libusb does

```
usb_class(...).connect()  -> Permission denied accessing 05c6:9008
usb.core.find(...) + set_configuration(1) + claim_interface(0)  -> OK
```

The 9008 interface: `class=0xff subclass=0xff proto=0x11`, endpoints `0x81 IN` /

Every tool built on `usb_class` (edl.py, LTBox via edlclient) failed on this, not on
the device.

## DISCOVERY 6 — a missing COM driver is not a configuration issue, it is a missing file

Every `oem*.inf` for `VID_05C6&PID_9008` and `_900E` in this system is
**libwdi/WinUSB**:

```
oem66  PID_900E  libwdi
oem67  PID_9008  libwdi  <- assigned
```

## DISCOVERY 7 — Lenovo's own tools can see 900E

`SwDownloadDLL.dll` contains the regex:

That pattern **matches "Qualcomm HS-USB Diagnostics 900E"**. So the factory Lenovo

## DISCOVERY 8 (breakthrough) — the melf is a CONTAINER with 5 ELF images

`xbl_s_devprg_ns.melf` **is not a single program**. It is a container. Scanning for
`7F 45 4C 46` headers:

```
offset      class   machine     entry         contents
0x000000    ELF32   0x01 ARM    0x22126000    wrapper / SBL loader
0x001300    ELF32   0xF3        0x20412D00    (3rd image)
0x032F70    ELF64   0xB7 ARM64  0x14825FA8    XBL core
0x110B50    ELF64   0xB7 ARM64  0x149997A8    *** FIREHOSE ***
0x15AB48    ELF64   0xB7 ARM64  0x1494E000    DDR training (dcb.bin, pre-DDR dtb, PLL/DRAM)
```

**Key:** image @`0x110B50` has `entry = 0x149997A8` — **exactly the same entry point
as `prog_firehose_ddr.elf`**.

So: **`prog_firehose_ddr.elf` is already inside the melf.** It is the same firehose
code. The separate file is rejected (`0x29`) because Sahara requires a melf container
— and the melf **contains** that firehose plus DDR training, which the standalone ELF
does not have.

### What this means in practice

Sahara accepts the melf in full (`END status=0x0`, 1 554 996 B), but our session ends
with `0xD` = `NAK_READ_DATA_ERROR`. Since the content is correct (it is the original
file from the package), the problem is in the **transport**, not the data:

- packet framing (fixed in v4+),
- ZLP after chunks that are multiples of 512 (added in v6),
- **and** the fact that the melf requires the full 1 569 028 B — while we send
  1 554 996 B.

**Difference: 14 032 B.** That is not a rounding artefact — it is a real difference
that needs explaining. The last packet may be truncated.

> **CORRECTION (added 2026-11-08):** wrong. Sahara requests only the images it needs;
> the trailing 14 032 B is padding it never asks for. The correct health check is
> `high_water` against the file size, not the byte count. See
> [`../docs/04-melf-format.md`](../docs/04-melf-format.md) §7.

## DISCOVERY 11 (most important) — the device GAVE THE REASON: `0x23`

After sending `SAHARA_RESET` (0x07) on 900E, the device responded:

```
04 00 00 00 | 10 00 00 00 | 23 00 00 00 | 01 00 00 00
cmd=END_TRANSFER  len=16      status=0x23   image_id=1
```

`0x23` = **`SAHARA_NAK_HASH_TABLE_NOT_FOUND`** — "I did not find the hash table in the
ELF image".

This is not a guess. It is **the device's own answer**. The programmer
(`image_id=1` = 32-bit prog) is rejected because PBL/XBL cannot find the hash table it
requires for verification.

### Why the melf passes and an ELF does not

```
xbl_s_devprg_ns.melf    1 569 028 B   ELF32 ARM   -> Sahara accepts (END 0x0)
prog_firehose_ddr.elf     303 096 B   ELF64 ARM64 -> Sahara rejects (END 0x29, after 64 B)
```

> **CORRECTION (added 2026-11-08):** the following paragraph is wrong. `0x23` was
> produced by a plain ELF that had already got past the header stage; it does not
> describe how melf verification works. The real container-level check is `0x21`, and
> it covers the whole blob — see [`../docs/06-signing.md`](../docs/06-signing.md).

~~Sahara for ELF32 (`melf`) accepts the transfer, but **at `END` it verifies the hash
table and returns `0x23`** when it is not in the expected place. For ELF64 it rejects
**immediately**, because it expects a melf.~~

### Signature coverage (DER `30 82` scan and CA names)

```
xbl_s_devprg_ns.melf   39 DER occurrences   Lenovo CA: YES   Qualcomm CA: YES
abl.elf                 9 DER occurrences   Lenovo CA: YES   Qualcomm CA: NO
xbl_config.elf          6 DER occurrences   Lenovo CA: YES   Qualcomm CA: NO
qtestsign: NONE in all three
```

So XBL accepts only images with a **Qualcomm SRoT** chain — while the ROCKNIX ABL
signed with `qtestsign` *was* accepted by XBL, but that is a different path (ABL is
not verified by Sahara).

## Hard conclusion

**Three layers block us at once:**

1. **Format** — Sahara requires `melf` (ELF32 with a hash table), not a plain ELF64.
2. **Hash table** — at `END` the device asks for it and returns `0x23`.
3. **Signature** — the melf must be signed with a Qualcomm SRoT / Lenovo CA chain.

We have a file that satisfies all three conditions (the original melf from the 18.5
package), but **the transport session breaks before `END`** — hence sometimes `0xD`,
sometimes `0x23`, sometimes a stall.

## What this means for the plan

There is no way to "bypass" the signature. But **we do not need to** — we have a
signed melf. The problem is purely about delivering all 1 569 028 B without losing
packets and without breaking the session.

This is a **USB transport problem, not a cryptography problem.**

## DISCOVERY 12 — the transfer is PERFECT, and firehose is silent

After fixing the entire transport layer, the Sahara session passes **without a single
error**:

```
HELLO ver=3 mode=0
END status=0x0 loops=37 bytes=1554996 high_water=1569028
DONE=True
```

- `END status=0x0` — the device accepts the image
- `DONE True` — the device confirms completion
- `high_water=1569028` — **the whole file was sent**, not a byte lost

So: **there is no longer a transport, framing or signature problem.** The earlier
`0xD` and `0x23` were the effect of a broken session, not a bad file.

### But after DONE, silence

Attempts to talk to firehose — all without an answer:

| payload | result |
|---|---|
| `<nop/>` × 6 | `0 B` |
| `<configure MemoryName="ufs" ZlpAwareHost="1" .../>` | `0 B` |
| `<configure ... ZlpAwareHost="0" .../>` | `0 B` |
| `<configure MemoryName="ufs"/>` (minimal) | `0 B` |
| `<configure ... MaxPayloadSizeToTargetInBytes="1048576"/>` | `0 B` |

The device **does not reject** these commands — it simply **does not answer**.

### What was observed about lifetime

```
DONE  -> 9008 node still present
      -> still present after ~24 s (as long as I hold the handle)
      -> after closing the handle: 9008 disappears, 900E returns
```

So the **programmer is alive**, but **does not re-enumerate as a firehose interface**.
USB on the device side was not brought up again.

### Possible causes (in order of probability)

1. **The programmer dies after start** — e.g. during UFS or DDR init. Then silence is
   natural, and the reset on handle close is only a side effect.
2. **The programmer is waiting for something we do not send** — but `nop` and four
   `configure` variants were excluded.
3. **The host USB (Windows/WinUSB) is not passing data** — even though
   `claim_interface` works and `write` does not raise an error.
4. **Battery/DBC** — the melf has `loader-dbc-threshold`, `skip-loader-dbc`,
   `battery-low-threshold-mv`, `charger is not charging and device will shut down`. If
   VBAT is below the threshold, the programmer **powers the device down** instead of
   starting.

### Point 4 is the most interesting right now

The melf contains, verbatim:

```
loader-dbc-threshold
skip-loader-dbc
vsys-min-recover-mv
vbatt-min
battery-low-threshold-mv
no-battery-charger-threshold-mw
low-battery-charger-threshold-mw
charger is not charging and device will shut down
battery recover failed
Loader dbc skipped. VBAT: %dmV
```

This matches the symptom exactly: transfer OK, DONE OK, then a **quiet death** instead
of firehose.

**Test to run:** charge the tablet fully (several hours on the mains charger, not USB),
then repeat exactly this session. If firehose comes up, power was the cause.

## DISCOVERY 13 (decisive) — this is not a transport or timing problem

I ran a catcher in a loop, catching the tablet in **every** boot cycle. Three
consecutive cycles, the same result to the second:

```
cycle 1: found 9008 -> HELLO ver=3 mode=0 -> END 0x0 -> DONE True -> cfg: silence
cycle 2: found 900E -> bump -> HELLO ver=3 mode=0 -> END 0x0 -> DONE True -> cfg: silence
cycle 3: found 900E -> bump -> ...
```

Every time:

- full upload of **1 554 996 B** (`high_water=1569028`, the whole file),
- `END status=0x0` — image accepted,
- `DONE True` — completion confirmed,
- then **total silence** on `<configure/>`, `<nop/>` and `SAHARA_MEMORY_DEBUG`.

And every time the device disappeared **~8 s after DONE** (`gone_at=29.26` with DONE at
21.35), regardless of what we sent.

### What this definitively excludes

| Hypothesis | Status |
|---|---|
| bad packet framing | **EXCLUDED** — `high_water` covers the whole file |
| missing bytes | **EXCLUDED** — 1 554 996 of 1 569 028 sent, the rest is `FF` padding |
| bad timing (too late) | **EXCLUDED** — `configure` sent 1 ms after `DONE` |
| wrong command (`nop` vs `configure`) | **EXCLUDED** — 5 variants, all silent |
| wrong programmer | **EXCLUDED** — the original melf from the 18.5 package, signed |
| broken transport | **EXCLUDED** — full cycle without an error |

### What remains

**The programmer is accepted but does not start as firehose on USB.**

Most likely, in order:

1. **The programmer dies during hardware init** (UFS or DDR) — then silence and a
   reset after ~8 s are natural. The melf contains `Entering DeviceProg DDR`,
   `sbl1_ddr_init`, `do_ddr_training` — if DDR training fails, the programmer dies.
2. **Battery / DBC** — the melf has `loader-dbc-threshold`, `skip-loader-dbc`,
   `vbatt-min`, `charger is not charging and device will shut down`. If VBAT < the
   threshold, the programmer **powers the device down** instead of starting. That
   would explain it perfectly: transfer OK, DONE OK, quiet death.
3. **Host USB** — but `claim_interface` works and `write` raises no errors, so less
   likely.

### The only sensible next steps

- **Charge the tablet fully** (several hours, mains charger, not the USB port) — tests
  hypothesis 2. Zero cost, potentially decisive.
- `skip-loader-dbc` — the flag suggests the battery test can be skipped. It requires
  modifying the melf, which breaks the signature. **Not feasible without the key.**
- Service / test-point EDL (a real 9008 from PBL, not via crashdump).

## DISCOVERY 14 (closing) — during the logo window the tablet DOES NOT EXIST on USB

I built a native watcher on SetupAPI (`FastUsbWatch.cs`, compiled with `csc`) — no WMI,
no libusb, no VID filters. It enumerates **all** USB nodes.

Measurement result:

```
[   0,001] baseline: 8 USB devices
[  42,517] - GONE    vid_05c6&pid_900e
[  57,501] + APPEAR  vid_05c6&pid_900e
[  90,005] === END: 584042 polls in 90,0s = 6489 polls/s (0,15 ms/poll) ===
new nodes: 1
```

**Resolution: 0.15 ms per poll. 584 042 polls.**

### What this means

For **15.0 seconds** (42.517 → 57.501) the tablet **was not present on the USB bus in
any form**:

- no `VID_05C6` with any other PID,
- no `VID_17EF` (Lenovo),
- no `VID_18D1` (Google/fastboot),
- no node without a driver.

If fastboot had appeared in the logo window, the watcher would have seen it at 0.15 ms.
**It did not appear.**

### Why the earlier scripts missed this

They all had `sleep(1)`–`sleep(6)` and a drain loop. For a 15 s window that should have
been enough — but they **did not look at all of USB**, only at `05C6:9008`/`900E`, and
they only started once the device was back on 900E. The logo moment was simply "no
device" to them.

The user's observation about the method was correct: **sleeps killed the resolution**.
But the result shows something more — in that window there was nothing to catch.

### What the tablet does during those 15 seconds

Since it is not on USB, it means either:

- **XBL/ABL is initialising hardware and not raising USB** (drawing the logo, loading
  the image, checking signatures),
- or **the programmer is doing DDR/UFS init** and only then (does not) respond on USB.

In both cases **the absence of the device from the bus is expected** — and nothing can
be done about it from the host in that window.

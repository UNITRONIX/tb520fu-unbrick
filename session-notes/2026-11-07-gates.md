## Gate 0 — atomic `edl`

**Setup.** `bkerler/edl` in atomic mode: bump `900E`→`9008`, then
`edl printgpt --memory=ufs --lun=4` to read the partition table as the first
operation, on the theory that a single-process session would own the window better
than a bump-then-connect sequence.

**Log, essential lines:**

```
Sahara … Loader successfully uploaded (ver 3, 64-bit)
HWID 0x2280e1 / OEM PKHASH logged
Firehose configure → USBError Pipe/IO
firehose_like = False
post: USB absent (logo phase)
```

**Result: FAIL.**

**What it established.** The atomic approach does not help. Even with the entire
session in one process, with no handle handoff and no race, Firehose does not come
up. This eliminated "our process model" as a cause and pointed at the device.

## Gate 1 — `QSaharaServer` + `fh_loader`

**Rationale.** These are Lenovo's own tools, shipped inside the RSA package. If
anything knows how to talk to this tablet's programmer, it is them.

**Setup problems, both worth recording:**

*Empty stubs.* The first run died with `WinError 193` (not a valid Win32 application).
`QSaharaServer.exe` and `fh_loader.exe` in the extracted kit were **0 bytes** — stub
files. The real ones were copied out of the stock RSA package
(176 128 B and 561 152 B respectively).

*CLI details.* The invocation required `-b` with a slash (not a backslash) and
`--sendxml=` rather than `--rawprogram=`.

**Log, essential lines:**

```
bump OK on COM5
QSahara: Sahara protocol completed, id 13, melf 1 554 996 B, rc=0
fh_loader: Failed to open com port \\.\COM5   (~9 s later)
device → logo → 900E (Diagnostics COM)
```

**Result: FAIL — same pattern as Gate 0.**

**What it established.** The COM world and the WinUSB world fail identically. The
driver model is not the cause.

## Gate 2 — LTBox

**Rationale.** Community reports had LTBox working on `TB520FU`. It performs an
atomic Sahara→Firehose session with its own client.

**UI problem.** The loader picker would flash the melf in the field for a moment,
then revert to `No file selected`. `settings.json` did receive the path
(`recent_paths`, `selected_at_ms`), so the wizard was clearing the selection —
likely because no device was connected at pick time. Workaround: connect the device
first, get `9008 Connected`, then use Flash Partitions with the remembered loader.

**Log, essential lines:**

```
QDLoader 9008 on COM6; LTBox Connected / EDL OK
loader: xbl_s_devprg_ns.melf OK
Sahara upload complete
Firehose: configuring
Firehose read failed: os error 995   (I/O operation aborted)
EDL session open failed
nothing written
```

**Result: FAIL — same pattern.**

## What all three gates share

| Step | Gate 0 | Gate 1 | Gate 2 |
|---|---|---|---|
| Bump to 9008 | OK | OK | OK |
| Sahara handshake | OK | OK | OK |
| Loader upload | OK | OK | OK |
| `END` accepted | OK | OK | OK |
| `DONE` | OK | OK | OK |
| Firehose configure | `USBError` | COM port gone | `os error 995` |
| Aftermath | logo → 900E | logo → 900E | logo → 900E |

Four tools, three process models, two driver worlds, two operating systems (Linux
was tested separately) — one outcome.

**The decision at the end of this day** was to stop trying tools and reimplement the
protocol from raw libusb, on the theory that all four tools might share a common
implementation assumption. That produced the protocol-level work in
[`2026-11-08-night.md`](2026-11-08-night.md) and
[`2026-11-08-morning.md`](2026-11-08-morning.md).

That was the right instinct and it paid off — it found three genuine bugs in our
understanding (framing, reset code, ZLP). It also proved the transport was never the
problem, which is what finally made the device-side explanation the only one left.

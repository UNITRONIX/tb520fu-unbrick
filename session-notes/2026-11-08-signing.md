# Signing with qtestsign — can the ROCKNIX key be "transferred"?

*Original: `QTESTSIGN_SIGNING.md`. Translated faithfully, including the section recording
the refutation of its own hypothesis.*

Date: 2026-11-08

---

## 1. Short answer

**Nothing needs to be broken. The key is public.**

The ROCKNIX ABL is signed with **qtestsign** keys — and qtestsign is an open-source tool
(GPL-2.0) that **contains the private keys in plaintext** in the file `mbn/cert.py`.

The authors' comment in the source:

```
NOTE: The certificate chain generated by qtestsign is NOT meant
to be secure. The private keys are listed here to make the
resulting files reproducible. THESE KEYS SHOULD ONLY BE USED
FOR TESTING AND NOT FOR A PROPER SECURE BOOT SETUP.
```

There is nothing there to break. The key lies in the open.

## 2. What qtestsign actually does

This is **not** cryptographic signing. It is packing an image into MBN format:

```
hashseg.generate(elf, version, sw_id):
  - adds an MBN header
  - computes the SHA256 of every ELF segment
  - adds a stub signature (256 B, ZERO — no real signature!)
  - adds a dummy certificate chain (qtestsign Root CA / Attestation CA)
```

As the qtestsign README says:

> "There is actually **no signature generated!** This works only for devices
> that have firmware secure boot **disabled**."

And further, about flashing already signed images:

> "qtestsign also accepts already signed firmware as input. In this case,
> **the original hash segment/signature is stripped and replaced with new hashes**."

**This is exactly the procedure that was being read about** — "transferring the key" onto
a valid image is one command.

## 3. What was achieved

We signed the firehose:

```bash
python qtestsign.py -v7 prog \
  -o prog_firehose_ddr-signed-v7.mbn \
  prog_firehose_ddr.elf
```

Result:

```
size:       303 104 B (original 303 096 B)
certificates: qtestsign Root CA - NOT SECURE
              qtestsign Attestation CA - NOT SECURE

MBN header:
  header_vsn_num  = 7
  cert_chain_ptr  = 0x100
  cert_chain_size = 1632
```

### Comparison with the ROCKNIX ABL that XBL ACCEPTED

| parameter | ROCKNIX ABL | our firehose |
|---|---|---|
| `header_vsn_num` | 7 | **7** ✅ |
| `cert_chain_size` | 1632 | **1632** ✅ |
| certificate type | qtestsign | **qtestsign** ✅ |
| SW_ID | 0x1C (abl) | 0x03 (prog) |

**The signature structure is identical.** Only `SW_ID` differs, which is correct —
firehose is `prog` (0x03), not `abl` (0x1C).

## 4. Why it might work — and why it might not

### Argument FOR

XBL accepted an ABL signed with qtestsign → **XBL accepts test certificates**.
That means secure boot at the ABL level is disabled.

Sahara was rejecting `prog_firehose_ddr.elf` with **`0x23` = HASH_TABLE_NOT_FOUND** —
the hash table was missing. qtestsign **adds exactly that table**.

So a signed firehose has a chance of passing where an unsigned one got `0x23`.

### Argument AGAINST

- XBL and PBL may have **different policies** — ABL verifies XBL, but PBL may require a
  different chain for the programmer.
- Error codes already seen: `0x23` (no hash), `0x29` (unknown, vendor), `0xD`
  (`READ_DATA_ERROR`). A signature solves `0x23`, but does not necessarily solve `0x29`.
- qtestsign generates **a zero signature** — if PBL checks cryptography (not just the
  presence of a hash table), it will not pass.

```bash

cd <KIT_DIR>
python firehose_race_2026-11-08.py    # but point it at the new .mbn file
```

Expectations:

- **success** → `END status=0x0` + firehose answers `<nop/>` → **write ABL immediately**
- **`0x23`** → the hash table still does not match (wrong MBN variant, try v6)
- **`0x29`** → PBL rejects the signature regardless of format → path closed
- **`0xD`** → transport problem, not signature

## 6. TEST RESULT (2026-11-08, ~00:45) — HYPOTHESIS REFUTED

The qtestsign-signed firehose was tested. Result:

```
signed-v7-prog   303 104 B   END status=0x29  after 64 bytes
signed-v6-prog   303 104 B   END status=0x29  after 64 bytes
signed-v7-abl    303 104 B   END status=0x29  after 64 bytes
```

**All three variants got `0x29` — identically to the unsigned file.**

### What this means

`0x29` appears **after 64 bytes**, i.e. after the ELF header alone — still before PBL
sees the hash table or the certificates. It is a **format rejection, not a signature
rejection**.

The qtestsign signature changed nothing, because the problem is not in the signature.

### Hard conclusion

**This device's PBL does not accept a plain ELF64 (AArch64) in any form** — signed or
unsigned. It accepts **only a melf** (ELF32 wrapper with 5 images, including firehose
@0x110B50).

This definitively closes the "sign the firehose and flash it" path.
Signing is not the bottleneck here — the format is.

### What remains untouched

1. **Signing the melf** — but a melf is an ELF32 container; qtestsign handles a single
   ELF. One would have to cut out the firehose image @0x110B50 (ELF64), sign it, and…
   upload it as a melf, which means wrapping it back in an ELF32 wrapper. That is
   possible, but requires writing a custom packer.
2. **Battery / DBC** — still untested (the tablet was charging overnight).
3. **Test-point EDL** — the only route to a real 9008 from PBL.

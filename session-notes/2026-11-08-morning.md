## 2. Signed melf — STILL 0x21 (confirmed, repeatable)

Test on a charged tablet, three variants:

```
original                : done_ok   1554996 B  ✅
signed v7 (+8 B)        : end_0x21  1109804 B  (3× identically)
signed v6               : end_0x21  1109684 B
signed SAME SIZE        : end_0x21  1109804 B  (exactly the same byte)
```

### Key observation

```
1 109 804 B  <  1 117 008 B  = offset of the firehose image (0x110B50)
```

The transfer breaks inside image **[2] (XBL core), which is UNTOUCHED**.

PBL verifies the integrity of **the whole blob**, not of individual images.

### Is the hash explicitly in the file? NO

Checked (`find_hashes.py`):

- SHA256 of each image — **ABSENT**
- MD5 — **ABSENT**
- wrapper (4 864 B) — a clean ELF32, the rest is zeros
- region `0x1000..0x1300` — empty

**The hash is computed in PBL and compared against a structure we cannot see.**

### Bypass attempt: identical size

The signed file is 303 104 B; image [3]'s slot is 303 096 B.
The signed file ended with 4 041 zeros → 8 B were trimmed → identical size.
The melf is **exactly 1 569 028 B** like the original, all offsets preserved.

**Result: the same `0x21`, the same byte.** Size was not the problem.

## 4. `DEVICE_DESCRIPTOR_FAILURE` — NOT a hidden EDL mode

The user's hypothesis: maybe the state with the missing driver is an EDL mode.

### Evidence against

| state | what the system sees |
|---|---|
| real EDL | `05C6:9008`, `mode=0`, full descriptors |
| `DESCRIPTOR_FAILURE` | `VID_0000&PID_0002`, no response |

`VID_0000` is a **Windows placeholder**, not a VID assigned by the tablet.
libusb **cannot see** such a device (it does not know the VID/PID).

### Registry — three different ports, the same error

```
8&1B878445&0&2   Port_#0002.Hub_#0002
8&384B90AF&0&4   Port_#0004.Hub_#0001
B&10BAF955&0&1   Port_#0001.Hub_#0007
   HardwareID = USB\DEVICE_DESCRIPTOR_FAILURE
```

If this were a mode, it would be one specific port. Three ports = **a hung PBL**.

### Cause

Replugging the cable **during** an operation blocked PBL halfway through USB
negotiation. Do not move the cable while the device is in EDL.

## 5. `DONE` after `END` — MANDATORY (new)

Test of four variants (`test_post_end_2026-11-08.py`):

```
VARIANT A: END -> <nop/> without DONE
  nop       -> 04 00 00 00 | 10 00 00 00 | 0d 00 00 00 | 01 00 00 00
  configure -> (identical)
  = cmd=END_TRANSFER, status=0x0D (NAK_READ_DATA_ERROR), image=1
  => the device is STILL in Sahara, it treated nop as a Sahara packet

VARIANT C: END -> Sahara EXECUTE (6 subcommands)
  all -> the same END status=0x0D
```

**Conclusion: without `DONE` the device does not move to devprg.**
The `END -> DONE` sequence was correct. Hypothesis closed.

---

## 6. Empty `END status=0x0` — a false success

Discovered by accident during the cable test:

```
HELLO ver=2 mode=2
END status=0x0  bytes=0/1569028     ← ZERO bytes
DONE_RSP cmd=0x6
```

A device in `mode=2` can accept a **zero transfer** and acknowledge `DONE`.
The script counted it as success — **incorrectly**.

**Correction for the future:** `END 0x0` with `bytes=0` is NOT success.
Require a full transfer (`bytes` >= payload size).
